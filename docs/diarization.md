# Local speaker identification

Speaker identification is an optional, separate post-processing stage. It uses trusted local ONNX segmentation and embedding models selected through the native file picker; the application performs no runtime model downloads. The CPU-only Sherpa 1.13.8 helper is isolated from capture and transcription.

Use compatible, approved models you are licensed to use. Sherpa's [official model documentation](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/index.html) is the primary source for compatibility information. Recommended, verified pair (see "Verified with real audio" below), both from the official [sherpa-onnx releases](https://github.com/k2-fsa/sherpa-onnx/releases):

- Segmentation: [`sherpa-onnx-pyannote-segmentation-3-0.tar.bz2`](https://github.com/k2-fsa/sherpa-onnx/releases/download/speaker-segmentation-models/sherpa-onnx-pyannote-segmentation-3-0.tar.bz2) (~7 MB; MIT license) -- extract and import `model.onnx`.
- Embedding: [`nemo_en_titanet_small.onnx`](https://github.com/k2-fsa/sherpa-onnx/releases/download/speaker-recongition-models/nemo_en_titanet_small.onnx) (~38 MB; CC-BY-4.0 license) -- import directly.

To import: Settings → "Identify speakers locally" → "Choose segmentation model" / "Choose voice model", each pointed at the corresponding `.onnx` file above. The app copies each into its own managed model storage by content hash; the original files are not needed afterward. Any other compatible pyannote-segmentation-shaped and embedding-extractor-shaped ONNX model pair works too -- these two are simply the smallest well-tested combination.

Jobs are bounded to 30 minutes per audio source and run **only on output (loopback) tracks** -- remote participants. The input (microphone) track is the local user and, after echo cancellation, should contain only them, so it is never diarized: this avoids wasted CPU and avoids one person's voice being spuriously split into several "speakers". Distinct remote voices are labeled "Speaker 1", "Speaker 2", … by order of first appearance within a source; an uncertain turn -- low clustering confidence, or competing with another candidate speaker -- falls back to "Remote" rather than guessing. Numbers are not named identities, are not comparable across recordings, and the same person appearing on a different audio source could receive a different number. A checkpointed companion JSON/Markdown result (`speakers.json`/`transcript-speakers.md`) preserves the original transcript unchanged. Retrying diarization does not retry Whisper. Missing speaker models or a diarization failure never blocks opening a completed transcript.

If diarization finishes only *after* a summary was already generated for the same recording, that summary simply predates the speaker labels; a summary rerun is an expensive local Ollama call, so this is not automatic -- use the existing "Regenerate" action on the summary once diarization completes to pick up the labels.

Disabling transcription also inhibits speaker processing.

## Verified with real audio

Native inference (release build, real sherpa-onnx 1.13.8, the two models above) was verified against several real local recordings' copied loopback tracks (6.9s-41.2s). All processed without a crash, at roughly 0.005x-0.12x real time (CPU) -- i.e. many times faster than real time -- and detected 1-3 distinct speakers per track depending on the actual number of remote participants, with turn boundaries that matched audible speaker changes. This verification also found and fixed two real bugs (see `src-tauri/src/diarization_real_tests.rs`, an ignored/env-gated test that reruns this check against locally-imported models and recordings without ever running in CI or depending on private data):

- **A Windows DLL-loading bug** (`src-tauri/build.rs`): sherpa-onnx's shared DLLs (`onnxruntime.dll` and friends) are copied beside the compiled *application* executable, which is exactly right for the shipped app, but `cargo test` binaries live one directory level down and fell through to an unrelated, older system-installed `onnxruntime.dll` (observed: a Windows ML/Copilot Runtime component's ORT 1.17, versus sherpa's bundled 1.28), crashing with an ONNX Runtime API-version mismatch. Fixed by also copying the DLLs beside test binaries at build time. The packaged application was never affected by this -- only local `cargo test` runs.
- **An out-of-range confidence value**: sherpa-onnx returns a sentinel (`-2.0`, observed on real single-speaker audio) rather than a real score when a turn's confidence cannot be computed (no second-nearest cluster to compare against). Passed through unchanged, this failed the app's own `0.0..=1.0` confidence validation, which would have made every single-speaker recording's diarization job fail outright. Fixed by normalizing any non-finite or out-of-range confidence to "unknown" (`None`), which downstream alignment already treats as an uncertain turn.

Clustering uses sherpa-onnx's own defaults (automatic cluster count, 0.5 distance threshold, 0.3s/0.5s minimum turn-on/off durations), which produced sensible turn boundaries on every real recording tested and were left untouched rather than hand-tuned against a handful of samples. macOS and Linux native inference remain unverified in this pass (Windows-only environment); both use their own platform-appropriate static Sherpa linkage and should behave identically, but have not been run.

Windows uses Sherpa shared-library companion DLLs; packaged builds must ship those DLLs beside the executable. macOS and Linux use their platform-appropriate static helper linkage.
