# Local transcription

## Scope and privacy

Whisper runs inside a single Rust background worker. Audio, model files, JSON checkpoints, and Markdown stay on this device. There are no runtime model downloads, external inference APIs, telemetry, summaries, or AppFlowy uploads in this increment. AppFlowy Cloud remains a later phase; optional speaker identification is documented separately in [diarization.md](diarization.md).

New recordings have an explicit `auto_transcribe` metadata flag. Missing flags deserialize to false: earlier hardware checks and legacy recordings are never automatically processed. The UI cannot submit arbitrary audio paths. Retry accepts only an existing job's recording ID; opening a transcript verifies its owned paths and saved contents.

## Models

Use Settings → Choose local Whisper model to import a trusted GGML `.bin` file, then select its size and save preferences. `base` is the default for a fresh install (small, fast to import, and does not force a first run to block on a large download); tiny/base/small/medium/large/**turbo** are recognized from model dimensions. English-only variants occupy the same size slot. No model is bundled.

**`turbo` (large-v3-turbo) is the recommended model** for real meeting audio: it is large-v3's encoder with a pruned 4-decoder-layer head, so it is dramatically more accurate than `base` at a similar CPU cost, especially quantized (e.g. `ggml-large-v3-turbo-q5_0.bin`, ~550 MB, from the [whisper.cpp Hugging Face repo](https://huggingface.co/ggerganov/whisper.cpp)). Settings shows it marked "(recommended)" with this same hint; there is no download button, so getting the file remains a manual, user-initiated download outside the app. Quantized files (q5_0, q8_0, ...) are recognized identically to f16/f32 ones: the GGML header's model-size dimensions (`n_audio_state`/`n_audio_layer`/`n_text_layer`) are independent of the `ftype` byte that records the quantization scheme, and `n_mels` (80 vs. 128) does not affect the size key either.

`distil-large-v3` (a 2-decoder-layer distillation, distinct from turbo's 4 layers) is explicitly rejected at import with a message pointing at `turbo`/`large` instead, rather than silently mis-classified as one of them — it has different accuracy/robustness tradeoffs (notably no built-in translation) that this importer does not want to paper over.

The official [whisper.cpp model instructions](https://github.com/ggml-org/whisper.cpp/blob/master/models/README.md) link available files. Prefer that upstream distribution over unknown model files. A manual download is network access made by the user, not the application. The upstream multilingual base file was verified through repository metadata as 147,951,465 bytes with SHA-256 `60ed5bc3dd14eea856493d334349b405782ddcaf0028d4b5df4088345fba2efe`.

Import validates the GGML header and size, hashes the file, copies it to `recordings/models/<sha256>.bin`, verifies the copy, and registers it in SQLite. Existing hash-named files are checked, not silently overwritten. Header validation does not prove all model weights are intact; the decoder performs full loading at transcription time and reports failures. Import only models you trust.

Changing the selected size affects newly queued jobs, and also re-points any job that has not yet been claimed (still `waiting_model`/`queued`) to the newly selected size, so it is not stuck on a size that was never imported. Once claimed, a job's exact model hash/path is pinned through retries and restarts regardless of later setting changes. Importing a model also switches the saved setting to it automatically when the previously selected size was not imported, so importing one model is enough to get transcription working. Large models can require substantial RAM even with four CPU threads; begin with base or tiny.

## Processing and output

The engine uses [whisper-rs 0.16](https://docs.rs/whisper-rs/0.16.0/whisper_rs/) and its bundled whisper.cpp, [Rubato 5](https://docs.rs/rubato/5.0.0/rubato/) for anti-aliased 16 kHz resampling, and Hound for PCM16 WAV decoding. Each source is downmixed independently and processed in bounded 60-second chunks. The model loads once per recording. Progress is chunk-based, not an estimated time remaining. Quit requests cancellation and waits off the UI thread for the worker.

### Language

Settings → Transcription language offers "Detect automatically" (default) plus English, French, Spanish, German, Italian, Portuguese, and Dutch. A pinned language is passed to Whisper for every decoded window of every track. "Detect automatically" instead detects once, from the first decoded speech window **per track**, and reuses that language for every later window of that same track — it does not re-detect every 60-second chunk, so a quiet or ambiguous chunk cannot flip the meeting's language mid-recording. The setting is read fresh at the start of each transcription job (unlike the model, it is not pinned into the job row), so changing it takes effect on the next job, not mid-run.

Transcripts record the language(s) actually used in `languages_used` (JSON only; sorted, deduplicated). Transcripts written before this field existed simply deserialize with an empty list — `validate_transcript` and checkpoint recovery do not depend on it.

### Acoustic echo cancellation

Every track — microphone and loopback alike — is decoded and resampled to mono 16 kHz `f32` exactly once per job (`transcription_engine::decode_track_16k`, called once per track up front by `decode_tracks_16k`), and that one in-memory buffer is shared by everything downstream: the VAD pre-pass, Whisper, and, for a recording with at least one `input` (microphone) track and at least one `output` (loopback) track — the common setup where the user listens through speakers rather than headphones, so remote participants' audio leaks into the mic and is otherwise transcribed twice, once per track, at nearly the same timestamps — acoustic echo cancellation. Cancellation runs directly on these shared 16 kHz buffers (mic against the sum of the loopback buffers as the reference, no further resampling needed since both are already at the same rate), before the silence pre-pass and Whisper, and before the recorder's own WAV files (which are never read a second time or modified). An hour of audio at 16 kHz mono `f32` is about 230 MB per track, held in memory for the duration of the job; earlier revisions of this pipeline instead decoded an `output` track twice (once natively to build the AEC reference, again resampled for its own transcription) and round-tripped a cleaned `input` track through a private temporary WAV purely to re-enter the same file-based decode path a second time -- both removed by sharing one decoded buffer per track (`transcription_engine::each_track_is_decoded_to_16k_exactly_once` pins this with a per-track decode-call counter). Controlled by Settings → **Cancel speaker echo** (`echo_cancellation`, default enabled; a no-op, regardless of the setting, on a recording missing either track direction). A completed transcript records in `## Processing notes` that cancellation was applied and against which sources, or, if it was a no-op for a track (e.g. a silent reference), nothing is recorded for that track since there was nothing to cancel.

Implementation (`echo_cancel.rs`) is an independent Rust module, not a binding to WebRTC or any other C/C++ AEC library; its architecture — a coarse delay/clock-drift estimator, a partitioned frequency-domain adaptive filter, a double-talk-aware step-size controller, and a residual-echo suppressor with a comfort floor — is modeled on the publicly documented design of WebRTC's AEC3 (see `echo_cancel/LICENSE-WEBRTC` for attribution). Two offline-only tricks it uses that a real-time canonical AEC cannot: (1) delay is estimated globally across the whole recording via GCC-PHAT, then re-estimated every 0.5 s with the shift *linearly interpolated* between estimates (not held constant per block), which corrects a slowly drifting delay (two independent USB devices' clocks, off by up to tens of ms an hour) essentially exactly rather than leaving a sawtooth for the adaptive filter to re-absorb every block; (2) the whole recording is run through the adaptive filter twice — once to converge the filter, discarded, then replayed from the start with the now-converged coefficients — so even the first seconds of a completed recording benefit from a fully converged filter, not just whatever it looked like on a first (and only) pass.

Simplified relative to full AEC3: one linear filter sized for the whole target echo-path length (~300 ms) rather than separate refined/coarse filters; a coarse energy-ratio (Geigel-style) double-talk detector comparing mic energy against the filter's own echo prediction, rather than a coherence-based one; and a residual suppressor that assumes a fixed fraction of the predicted echo leaks through, rather than a trained residual-echo model. A block whose reference has essentially no far-end energy anywhere in the recording's loudest activity (`far_end_active_mask`, gated at -26 dB below the recording's own peak reference level) bypasses the filter and suppressor entirely for that block, so a stretch with nothing legitimate to cancel cannot be suppressed based on a misclassified double-talk ratio or an overfit filter weight; a synthetic regression test (`near_end_only_audio_is_preserved_within_one_and_a_half_db`) pins near-end-only attenuation to within 1.5 dB. It is not a substitute for headphones.

Adaptive-filter block period is 20 ms, not the 10 ms conventional for a real-time AEC: since this canceller is offline and replays the whole recording twice anyway (see above), doubling it roughly quarters the dominant per-block cost (the gradient-constraint FFT pair paid once per filter partition per block) for a large net speedup, at the acceptable cost of halving the double-talk detector's and filter's time resolution — safe here because `echo_cancel::delay` already removes essentially all linear drift before the filter ever sees the signal. On a real ~41 s two-track recording (3950X, release build), `cancel_echo` alone now runs at roughly 50-60x real time (`echo_cancel::bench`, a manual, `#[ignore]`d benchmark against real recordings via `AEC_BENCH_MIC`/`AEC_BENCH_REF` env vars), up from roughly 20x before this: the dominant earlier cost was not the FFT work but `delay.rs`'s full-range GCC-PHAT fallback search firing on most blocks of real (broadband, non-tonal) audio, because its score floor was calibrated against near-pure-tone synthetic fixtures rather than real recordings' much noisier typical score; it now requires two *consecutive* low-score blocks (`REACQUIRE_STREAK`) before paying for that search.

Cancelling a 41 s clip taking on the order of 1 second used to still show up as a large end-to-end wall-time difference between transcribing raw vs. AEC'd audio, for two additive reasons found by instrumenting real recordings (CUDA, turbo): removing loopback bleed-through from a mic track reveals the near end's *real* pauses, which used to be masked by continuous (falsely "speech") echo energy filling every gap in `transcription_engine.rs`'s energy-based pre-pass, so the same conversation VAD-fragments into many more, much shorter regions, and Whisper pays a large fixed per-window decode cost (state setup plus, on the GPU path, a roughly constant-ish encoder pass) regardless of how little audio a window holds; and `cancel_echo`'s own cost, while small, used to be pure serial overhead on top of Whisper decode time because it ran to completion before the Whisper context was even created. `VAD_MERGE_GAP_MS` (1200 ms, up from 1000) re-merges most of the fragmentation without the failure mode a much larger gap has: bridging a genuinely silent multi-second stretch into one mostly-silent window that Whisper can hallucinate a stray word onto with a wildly wrong timestamp span. Since `apply_echo_cancellation` touches no Whisper state, it now runs on a background thread concurrently with the main thread creating the (possibly GPU) context and decoding every `output` track (AEC never substitutes those); only `input` tracks wait on its result. Measured on 5 real two-track recordings (CUDA, turbo, RTX 3060 Ti), raw vs. AEC'd total wall time: 4 of 5 came out equal or faster with AEC on; the remaining one (the most fragmented near-end speech of the set) is still about 14% slower, which would need a density-aware region-merge heuristic rather than a blanket gap increase to close further.

Even with the AEC above, some duplicate mic/loopback lines can still reach the transcript: signal-level cancellation is imperfect, and it is skipped entirely for a track when `echo_cancellation` is off or AEC failed for that track. `echo_dedup.rs` is a second, text-level pass after transcription: it drops a microphone segment when a loopback segment overlaps it within 1.5 s and their normalized (lowercased, diacritic-folded, punctuation-stripped) word-Jaccard similarity is at least 0.6 — a near-verbatim echo, not a partial double-talk overlap, which naturally scores lower and is kept. A loopback segment is never dropped. Controlled by Settings → **Remove duplicate echoed lines** (`dedupe_echo_segments`, default enabled, independent of `echo_cancellation`); the number of segments removed is recorded in `## Processing notes` when nonzero.

### Silence skipping and anti-hallucination

Within each 60-second chunk (after resampling to 16 kHz mono), a lightweight energy-based pre-pass (`detect_speech_regions` in `transcription_engine.rs`) finds likely-speech regions before anything is decoded: 20 ms frames, RMS compared in dBFS against an adaptive noise floor (the quietest 20% of this chunk's own frames) plus a 12 dB margin, never below an absolute -60 dBFS floor. Raw speech runs under ~250 ms are dropped as noise spikes (checked *before* padding, so hangover padding cannot rescue a spike into looking like real speech); surviving runs are padded ~300 ms on each side, and gaps under ~1 s between padded regions are merged. Whisper.cpp's own VAD needs a separate Silero GGML model file we do not bundle or offer to import, so this is a purpose-built substitute, not that VAD.

A chunk with no detected speech region is never decoded at all — this is where the biggest win is on real recordings with long one-sided silence (e.g. one participant's microphone track while only the other speaks), both for wall time and because Whisper is prone to hallucinating repeated filler ("Thank you.", music-video credits, etc.) on near-silent input. Surviving regions are decoded in windows capped at 30 seconds (a region longer than that is split into equal-sized ≤30 s windows); segment timestamps are mapped back onto the window's exact sample offset and then the chunk's offset, so they land on the original recording's timeline exactly regardless of how many silence gaps were skipped. A track that is entirely silent produces zero segments and no error.

Each decoded window also sets `suppress_blank`, `suppress_non_speech_tokens`, a temperature-fallback schedule (0.0 with a 0.2 increment), and `no_speech_thold`; segments whose reported no-speech probability is ≥0.85 are dropped rather than surfaced as text. None of this is a substitute for a real VAD model or a language model rescoring pass — it reduces, but does not eliminate, hallucinated text on genuinely ambiguous audio.

For each recording:

```text
recordings/<recording-id>/
  track-00.wav
  track-01.wav
  transcript.json
  transcript.md
```

Markdown includes the recording's UTC start date/time, duration, stable ID, model size, audio sources, timestamps, and capture/processing warnings. Passage text is escaped as literal Markdown so recognized text cannot silently embed external images or executable HTML. No summary is generated.

Device labels are **not speaker labels**. Multiple sources can still contain overlapping or duplicate speech — acoustic echo cancellation plus the text-level dedup pass (above) together reduce, but do not eliminate, mic-vs-loopback duplicates, and neither does anything for two genuinely separate microphones picking up the same talker. There is no speaker recognition. Chunk boundaries can split/repeat words. Whisper may still misrecognize speech or hallucinate on ambiguous nonspeech even with the silence pre-pass and anti-hallucination decode settings described above; exact digital silence and detected-silent regions are skipped, but this remains a coarse energy-based gate, not a full voice-activity-detection model. Captures with retained gaps can be transcribed and remain labelled incomplete.

## Durable states

`transcription.sqlite3` is separate from capture metadata. One job per recording ID transitions from queued → waiting_model or transcribing → completed/failed. Claims are conditional; attempts, model identity, artifact paths, and transcript hash persist. Failed jobs do not spin in an automatic retry loop: use Retry transcription.

JSON is flushed and renamed first, then Markdown, then the completion transaction. On restart, abandoned claims are requeued. If a valid matching JSON checkpoint exists, Markdown is completed without rerunning Whisper. Corrupt/mismatched checkpoints and conflicting Markdown fail closed and stay on disk for inspection. Completed jobs are never automatically retranscribed, including when an artifact is missing. The Open transcript action checks integrity and reports missing/modified files; editing Markdown yourself does not cause the app to overwrite it.

The application is not a backup system. Keep backups of the recordings directory; native filesystem durability across sudden power loss still requires platform testing.

## Build and verification

Whisper requires a C++ toolchain, CMake, and libclang at build time; no Python interpreter or libclang is shipped as an application runtime dependency. `LIBCLANG_PATH` must point to the directory containing the appropriate libclang shared library. Do **not** set `WHISPER_DONT_GENERATE_BINDINGS=1` on Windows: this locked sys crate's bundled bindings contain Linux-specific types.

On this development host, [libclang 18.1.1](https://pypi.org/project/libclang/18.1.1/) was installed only into `.tools/libclang` using `python -m pip install --target .tools/libclang --no-deps --only-binary=:all: libclang==18.1.1`. The convenience `scripts/dev.ps1` discovers its DLL without changing system configuration. Other developers can use their normal LLVM installation.

`.cargo/config.toml` disables host-native compilation (`GGML_NATIVE=OFF`) but enables the AVX/AVX2/FMA/F16C build flags, i.e. an x86-64-v3 baseline. Essentially every x86_64 CPU sold since ~2013 (Haswell/Excavator onward) supports this, so it is still a portable baseline, just a less conservative one than "no SIMD at all" — measured at roughly 2.7x faster than the pre-AVX2 baseline on this development host (see Benchmarking below) even before accounting for the higher thread count. Distributors targeting older hardware can override these flags outside this repository. Native macOS/Linux builds and permissions remain unverified on this Windows host. CI includes all three targets but a configured matrix is not evidence of a completed run.

Whisper thread count (`transcription_engine::cpu_threads`) uses `std::thread::available_parallelism()`, clamped to `[1, 16]`, instead of a hardcoded 4; this scales decoding across the logical cores actually available up to a point where hyperthread/SMT siblings stop helping.

### Optional GPU (CUDA) transcription

CUDA support is an opt-in Cargo feature (`cuda`, wired to `whisper-rs/cuda`) and is **not** part of default builds, so CI and non-NVIDIA machines are unaffected. To build with it:

- Install the CUDA Toolkit (12.x or 13.x) so `nvcc` and the CUDA headers/libs are on `PATH`/`CUDA_PATH`. This is a separate, larger install than the driver alone.
- `CMAKE_CUDA_ARCHITECTURES` is set to `86` (Ampere, e.g. RTX 30-series) in `.cargo/config.toml` to keep compile times down; it is a harmless, unused CMake define when the `cuda` feature is off. Override it (or set the `CUDA_ARCHITECTURES` env var equivalent for your GPU) if you have different hardware — see [CMake's CUDA_ARCHITECTURES docs](https://cmake.org/cmake/help/latest/prop_tgt/CUDA_ARCHITECTURES.html) for the code for your GPU generation.
- Run `npm run tauri:cuda` (dev) or `npm run tauri:build:cuda` (release build), or `scripts/dev.ps1 -Cuda`, which also puts `%CUDA_PATH%\bin` on `PATH` when `CUDA_PATH` is set.
- A CUDA build's runtime needs the CUDA runtime DLLs (`cudart64_*.dll`, `cublas64_*.dll`, etc.) reachable — either the CUDA Toolkit's `bin` on `PATH`, or those DLLs copied beside the built executable for distribution to machines without the Toolkit installed.
- At runtime, the engine tries to create a GPU Whisper context first; if that fails (no compatible GPU, driver mismatch, etc.) it logs a warning and transparently falls back to the CPU path rather than failing the transcription job. The active backend (`"cpu (AVX2)"` or `"cuda"`) is reported by `get_transcription_state` and shown in Settings next to the model status.
- Flash attention (`WhisperContextParameters::flash_attn`) is enabled on the GPU context. The Whisper context itself is created once per transcription job (`LocalWhisperEngine::transcribe`) and reused across every track and chunk within it, not recreated per track; only the lightweight per-window decode state (`context.create_state()`) is per-window. On a real ~41 s two-track recording (RTX 3060 Ti, turbo, CUDA release), end-to-end wall time (decode+resample, VAD, Whisper for both tracks, dedup; no AEC) is roughly 3.6-3.9 s versus ~740 s on the same recording, same model, CPU-only (see Benchmarking) -- almost entirely the GPU-vs-CPU Whisper decode difference, not a change made in this pass. One further opportunity was identified but not applied: enabling flash attention on the CPU path too (whisper-rs 0.16 exposes it as a plain context flag, not GPU-gated) was not verified to leave CPU output byte-identical within the time available for this investigation, and would need that verification before shipping. (An `output` track being decoded twice when echo cancellation was on used to be a second such opportunity; it no longer applies now that every track is decoded once and shared -- see "Acoustic echo cancellation" above.)

### Benchmarking

There is no benchmark harness checked into the repo (a prior throughput number came from an ad hoc, temporary `#[ignore]`d test against a real recording, which was removed after use — never commit a test that reads real user recordings). To reproduce: copy a completed recording's folder and an imported model's `.bin` out of `%APPDATA%\com.local.meetingrecorder\recordings\...` into a scratch directory, write a temporary `#[ignore]`d test in `transcription_engine.rs` that builds a `TranscriptionRequest` against those copies and times `LocalWhisperEngine::transcribe`, run it with `cargo test --release -- --ignored --nocapture`, then delete the test.

The most recent such run compared a real ~41 s two-track meeting recording (the same one behind the "I completely co-emerge in migration to" complaint) on the `base` model, release build, same AVX2 baseline (commit `d55f060`) before vs. after the turbo/language/silence-skip change in this document, on the same development host:

| | wall time | segments | first lines |
|---|---|---|---|
| before | 32.1 s | 25 | `I completely co-emerge in migration to` / `the virtual machine and script first information` |
| after | 34.3 s | 16 | `completely co-emerge in migrating to the virtual machine.` |

Wall time is essentially unchanged (slightly slower) on this recording specifically because it is two people talking almost continuously — there is little silence for the pre-pass to skip, so its only effect here is windowing/anti-hallucination decode settings, not skipped decode work. The quality difference is the real result: fewer, better-formed segments and no more visible mid-word garbling in the sampled lines. The silence-skipping win is expected to dominate on recordings with long one-sided silence (e.g. one participant's track sitting quiet while the other talks), which this particular short fixture does not exercise; it was not re-measured against a long-silence fixture because none was available in the scratchpad. Reproducing the pre-AVX2 baseline (commit `050c614`, one commit before `d55f060`) would need a second full whisper.cpp CMake build in an isolated worktree; given the wall-time result above is not the interesting comparison for this change, it was not run.

A separate ad hoc run (also removed after use), transcribing that same real ~41 s recording on `turbo` instead of `base`, CPU release build, no CUDA: roughly 740 s wall time, an ~18x real-time factor. `turbo`'s much larger encoder (large-v3's, 32 layers/1280 state) dominates cost regardless of its pruned 4-layer decoder, so it is dramatically slower than `base` on CPU per second of audio despite the "similar CPU cost... especially quantized" framing above, which is about accuracy-per-cost versus `large`, not an absolute claim against `base`. Prefer the `cuda` feature (see below) for `turbo` on any recording longer than a couple of minutes.

A further ad hoc run (also removed after use), on `turbo`, CUDA release build, RTX 3060 Ti, comparing raw vs. AEC'd total wall time (decode+resample, AEC when on, VAD, Whisper for every track, echo dedup) across 5 real two-track recordings ranging from ~7 s to ~41 s:

| recording | raw | AEC'd |
|---|---|---|
| a | 1.95 s | 1.51 s |
| b | 2.69 s | 3.06 s |
| c | 2.88 s | 2.33 s |
| d (the ~41 s one above) | 3.57 s | 3.57 s |
| e | 1.88 s | 1.97 s |

CUDA turns the ~740 s CPU `turbo` number above into low single-digit seconds for a ~41 s recording -- roughly 200x, not just the AVX2 baseline's ~2.7x -- because the encoder pass (`turbo`'s dominant cost) parallelizes far better on a GPU than AVX2 SIMD. Recording (b) is the one recording of the 5 still slower with AEC on (~14%): it has the most fragmented near-end speech of the set (many short utterances genuinely separated by silences just over `VAD_MERGE_GAP_MS`), so each extra Whisper window's fixed per-window cost is not fully offset by overlapping `cancel_echo` with GPU decode. See "Acoustic echo cancellation" above for the root cause and fix.

Synthetic tests use a fake engine and isolated files, never existing microphone recordings. The ignored `transcribes_explicit_public_fixture` test requires explicitly supplied `WHISPER_TEST_MODEL` and `WHISPER_TEST_AUDIO`; it makes no downloads. Do not point it at private recordings without separate consent.

For native UI checks set **both** `MEETING_RECORDER_DISABLE_AUTOMATION=1` and `MEETING_RECORDER_DISABLE_TRANSCRIPTION=1`. The second prevents audio reads/job claims, including after restart. Model import alone does not override that inhibition.
